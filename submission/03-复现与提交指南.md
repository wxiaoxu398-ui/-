## 上传作品并记录核验提交

由有仓库权限的维护者执行，普通使用者可只按前文克隆和启动。先检查 `git remote -v`、当前分支及待提交内容，确认 `origin` 对应上述真实仓库；如配置不同，先查清用途，不覆盖不明远端。源码与原有开发历史一并保留，不删除历史后重新初始化。

1. 上传前复查待提交文件，排除真实 `.env`、实际团队 JSON、报名参考链接、数据库、用户会话、模型缓存、PDF 教材、依赖目录和构建缓存。
2. 由维护者确认目标分支名，再进行正常推送；不使用强制推送，不删除远端分支，不擅自修改仓库可见性、默认分支或评审权限。
3. 若远端包含本地尚未合并的历史，正常推送可能被拒绝。此时停止，先检查双方提交并由维护者处理合并；不要用 `--force` 绕过拒绝。
4. 推送后重新读取实际目标分支的完整 SHA，核对是否等于本次准备归档的本地 HEAD。不要只凭命令开始执行或 `origin` 配置就写“已上传”。

本轮已核实目标为 main。后续维护时仍先确认远端配置，再输入实际目标分支：

```powershell
$publishBranch = Read-Host '输入团队确认的远端目标分支名'
git check-ref-format --branch "$publishBranch"
if ($LASTEXITCODE -ne 0) { throw '分支名无效，停止上传。' }
git push --set-upstream origin "HEAD:refs/heads/$publishBranch"
if ($LASTEXITCODE -ne 0) { throw '推送没有完成，先检查远端历史与权限。' }
$remoteLine = git ls-remote --heads origin "refs/heads/$publishBranch"
if ($LASTEXITCODE -ne 0 -or -not $remoteLine) { throw '未读到目标分支，不能记录上传成功。' }
$verifiedCommit = ($remoteLine -split '\s+')[0]
$localHead = (git rev-parse HEAD).Trim()
if ($verifiedCommit -ne $localHead) { throw '远端 SHA 与本地 HEAD 不同，不能确认当前归档提交已上传。' }
```

上述读取证明的是当前访问者在目标仓库能读到该提交，并不自动证明匿名评审或指定评审账号有权限。提交前仍需按赛事要求核验评审访问，明确分支或提交入口，并同步到官网表单。项目许可方式和第三方声明由团队确认，本次不替团队选择开源许可证。

## 按 2026-11-11 版本重新打包

先提交准备纳入源码的文本，再生成并逐页审阅 PDF。已有旧包不会被覆盖；需要重做同一天材料时，指定项目内部一个新的绝对输出目录。

若刚刚通过远端读取取得 `$verifiedCommit`，可把该完整 40 位 SHA 作为核验记录传入。本轮重新生成并检查的 PDF 为 **11 页**；PDF 再变动后须使用重新核实的实际页数，且不得超过 30 页：

```powershell
.venv\Scripts\python.exe submission/build_package.py --date 20261111 --pdf-pages 11 --repository-verified-commit "$verifiedCommit"
```

脚本还会本地检查 `origin` 规范化后确实对应 `https://github.com/wxiaoxu398-ui/-`，并要求该 SHA 是当前 HEAD 的祖先。只有核验 SHA 与包中 HEAD 相同，才能记录“本包 HEAD 已在该远端核验”；如果只核验到较早的祖先提交，索引和 manifest 会明确“仅已上传至该历史提交，本包 HEAD 尚未确认上传”。不要把本地 `git rev-parse HEAD` 的结果冒充远端读取记录。

没有远端核验记录时可以省略 `--repository-verified-commit` 整理本机材料，但生成的包不能宣称当前 HEAD 已上传。默认输出为 `deliverables/MedRAG-Submission-20261111/` 及同级总 ZIP。实际团队 JSON 只进入本机交接目录，公开源码继续只包含示例模板。

本轮还通过禁用 Git 凭据助手的读取验证了公开访问。只有针对当前核验提交实际完成相同检查时，才可附加 `--repository-public-read-verified`；该参数记录外部检查结果，打包脚本本身不联网。
